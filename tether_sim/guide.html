01 / THE BIG PICTURE

One drone. A moving load.
Two layers of control.

The payload keeps swinging after the drone moves. The controller must move the drone while managing the load below it.

The current AI is a helper around a conventional controller. The PD controller still does the stabilizing. The neural network learns small motor adjustments. It is not yet a self-contained pilot.

The simulator

MuJoCo calculates motion, motor lag, gravity, cable-link motion and contacts. The visual mesh makes the drone recognizable; separate geometry controls collisions.

The task

Lift a hanging payload, carry it to a target, and settle. Success should involve load accuracy, limited swing and avoiding collisions.

The policy

A neural network reads simulation state and outputs four numbers. Each is a correction to one motor command.

02 / WHAT THE POLICY SEES AND DOES

A policy is a decision rule.

In our first run, its input contains position, orientation, velocities, cable joint states, motor thrust, target, wind, time and previous corrections. These are privileged simulator values.

ObserveRead the simulated state
NormalizeScale inputs using saved statistics
PredictTwo 256-unit hidden layers for the actor
CorrectAdd four bounded motor adjustments
SimulateAdvance motion and repeat

50 decisions per simulated second

The control interval is 20 milliseconds. MuJoCo integrates ten 2 ms physics steps during each decision. The browser renders independently, typically around 25 FPS in our earlier sample.

The camera is not the input yet

The grayscale camera view is synthetic. It is displayed and can generate data, but the current controller does not detect squares or tether geometry from pixels. Your existing square detector remains a separate component.

TRY IT / ONE MOTOR, ORIGINAL V002 POLICY

How much authority does the AI have?

Illustrative baseline motor force: 0.120 N. Slide the policy's output between −1 and +1.

0.120 N + 0.0000 N = 0.1200 N

V002: output × 0.05 normalized command × 0.20 N = up to ±0.010 N per motor. V003 uses a smaller ±0.006 N correction. Commands remain clipped to the motor range.

Normalization is part of the trained model. The ZIP checkpoint and its matching normalization file must be loaded together. Feeding residual actions directly into the raw motor environment would use the wrong action contract.
03 / HOW TRAINING WORKS

Try, measure, update. Repeat.

Collect flight experience

Four simulation environments produce state, action, reward and next-state sequences. These physics rollouts run on the CPU.

Score the behavior

The reward penalizes payload target error, drone target error, swing, excessive motor corrections and abrupt changes. Crashes incur an additional penalty.

Update the policy with PPO

PPO estimates which actions were better than expected and updates the network, while limiting how far action probabilities move in one update. Our policy updates run on the GTX 1070 Ti.

Evaluate without learning

Run the saved policy and PD under matching conditions. Compare payload tracking and crashes. A higher training reward alone does not establish a better controller.

The original reward, in plain terms

reward = −1.5 × payload distance −0.5 × drone distance −0.1 × swing angle² −0.01 × correction effort −0.01 × correction changes −25 if the drone crashes

Distances are meters; swing is radians. Observation/reward normalization changes their training scale. These weights are design choices, not laws of physics. V003 adds obstacle/clearance penalties and stronger correction regularization.

250,880

Transitions in V002

One transition is one simulated control decision, not one rendered video frame. PPO collects complete rollouts, which slightly exceeded the requested 250,000.

8½ min

Training run duration

510.24 seconds recorded, including evaluations, excluding Python/CUDA startup.

CPU → GPU

Different jobs

CPU simulates physics; GPU updates the neural network. Live playback uses CPU inference. GPU use does not imply GPU physics or a speedup for this small network.

05 / FROM ONE FLIGHT TO MANY

Generalization has to be tested.

A policy that succeeds on one path can memorize that situation. The next task changes the conditions, adds physical gate posts, and gives the policy obstacle information.

What V003 can observe

The previous state plus obstacle geometry, route goal and physical domain parameters. This is still privileged state. It is a starting point for robust simulated control, not perception-based navigation.

What the obstacles test

The gate is placed across the carry route with room through its center. This tests clearance under disturbances. It does not yet test choosing a route around an arbitrary blocked path.

Separate training, validation and test cases. Training varies seeds. Five validation seeds select checkpoints. Ten separate test seeds are reserved for the final evaluation. The new configuration requests 100,000 steps or 15 minutes. Check the live run status for whether training has started or finished.

The new actor starts with zero mean residual, so its initial deterministic behavior matches PD. Smaller updates and exploration aim to avoid disrupting that baseline. Whether it improves or transfers remains an empirical question.

Why can’t the old checkpoint just avoid the new obstacles?

Its inputs did not contain obstacle geometry, and its training did not penalize obstacle collision. V003 changes the observation contract. Loading the old network into that new contract would be invalid; the new task starts a separate model.

07 / WHAT IS STILL MISSING

A useful simulator is not proof of real flight.

Is the tether a physically accurate rope?

It is a chain of rigid capsule links with ball joints, damping and small numerical armature. It can fold and contact geometry, but rigid links can transmit compression. Stretch, bending stiffness and real rope friction are not identified. We need hardware measurements and comparison with higher-fidelity cable models.

Are we doing camera-based tether control?

No. The policy reads privileged simulation state. A vision stage must estimate the relevant state from camera frames, deal with latency and uncertainty, and pass separate perception evaluations before closed-loop use. Existing square detection is a useful component, not a completed vision controller.

What does “generalizable” mean here?

At minimum, consistent performance on new seeds, routes, payloads, winds and obstacle layouts within a declared test distribution. Transfer outside those ranges, arbitrary obstacle routing and real hardware are separate claims requiring separate tests.

What would justify calling this SOTA?

Comparative evidence against strong baselines, validated physics, robust held-out evaluations, reproducible throughput and real-system relevance. A good-looking 3D scene and a trained neural network do not establish that.

What did we check already?

Gym contracts, finite actions, mass/length consistency, freefall, PD scenarios, timestep convergence, static load, cable folding/contact, reproducible seeds, physical obstacle contacts and seeded route sweeps. The saved V002 best policy reproduced its recorded evaluation to numerical precision after reloading. These are scoped checks, not a hardware validation campaign.
